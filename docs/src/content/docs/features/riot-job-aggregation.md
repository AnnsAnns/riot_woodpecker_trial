---
title: RIOT job aggregation
description: How RIOT turns one Murdock job into many build and test subjobs, then aggregates their status and results.
---

Murdock sees one job for a pull request, branch, tag, or commit. RIOT then
fans that job out into many build and test commands. This page explains how
RIOT collects those results back into the single Murdock job.

Aggregation is the process of collecting many subjob results into one Murdock
job. A subjob is one command in the RIOT job list, for example one application
on one board with one toolchain.

## One job, many subjobs

```text
PR / push / manual
       │
       ▼
  Murdock job  (one UID, one job token, one status)
       │
       ▼
  murdock-scripts/build.sh
       │
       ├── .murdock get_jobs
       │      ├── compile job: app A, board X, gnu
       │      ├── compile job: app A, board Y, gnu
       │      ├── run_test job: app A, board X (native, emulated, or legacy test_job)
       │      └── static_tests
       │
       ▼
  dwq queue and worker fleet
       │
       ▼
  result.json + status:: queue
       │
       ├── reporter.py -> PUT /job/<uid>/status
       └── process_result.py -> builds.json, tests.json, stats.json, ...
```

The Murdock server does not create a job for every build or test. It runs one
script and receives progress through the job status endpoint. RIOT owns the
fan-out and the aggregation.

On murdock-ng, `MURDOCK_NUM_WORKERS` limits top-level jobs. It does not create
one worker per build or test. The RIOT wrapper controls the subjob fan-out.

## Discovery

The legacy RIOT entry point is `murdock-scripts/build.sh`. Its job discovery
step is:

```sh
get_jobs() {
    dwqc ${DWQ_ENV} './.murdock get_jobs'
}
```

`.murdock get_jobs` prints the job list:

```text
./.murdock static_tests
./.murdock compile tests/sys/shell samr21-xpro:gnu
```

A compile job can spawn a `run_test` job for native or emulated boards. The
legacy `test_job` helper can also emit one.

`build.sh` sends that list to `dwqc`. Each line becomes one dwq job. The
`DWQ_JOBID` and `--subjob` flags link the compile and test jobs to the parent
Murdock job.

## Dispatch and queues

RIOT uses several queue names:

| Queue | Used by |
| --- | --- |
| `default-first` | Compile jobs generated by `.murdock get_compile_jobs` |
| `default` | General build workers |
| `<board>` | `run_test` jobs from the legacy `test_job` helper, for example `samr21-xpro` |
| `<hostname>` | A worker can also listen on its own hostname |

A worker starts with:

```sh
dwqw --name <hostname> --queues <hostname> default-first default --jobs 1
```

If a wrapper uses `test_job`, a test worker listens on the board queue. This
routes the `run_test` job to a worker that has the board connected. The current
`.murdock` script does not call `test_job`. It runs `make test-murdock` on the
compile worker instead.

Native and emulated tests do not need separate hardware. RIOT runs them inline
with `dwq-localjob`:

```sh
dwq-localjob \
  --command-override "./.murdock run_test ${appdir} ${board}:${toolchain}" \
  -- make -C${appdir} test
```

The command override makes the result appear as a test job in the Murdock
output and UI instead of appearing as part of the compile job.

If a separate job calls `run_test`, that job must build the application first.
`run_test` expects the binary in `$(pwd)/build`.

## Live aggregation

`build.sh` starts a reporter before it submits the job list:

```sh
report_queue="status::${CI_JOB_UID}:$(random)"
reporter.py "${report_queue}" "${CI_JOB_UID}" "${CI_JOB_TOKEN}" &
```

The `--report` flag makes `dwqc` publish subjob status to that queue as jobs
finish. The reporter reads those messages and builds the aggregate.

`reporter.py`:

- saves build and test output to
  `output/<type>/<app>/<target>:<toolchain>.txt`,
- saves other output to `output/<name>.txt`,
- parses the command to find the subjob type, application, target, and
  toolchain,
- counts failed jobs, failed builds, and failed tests,
- keeps at most 20 entries in each failure list,
- adds an `and N more ...` entry when a list is truncated,
- sends no more than one status update every 0.5 seconds,
- sends a final update when the report queue receives `done`.

The status body looks like this:

```json
{
  "status": "working",
  "total": 123,
  "passed": 80,
  "failed": 2,
  "eta": "12",
  "failed_builds": [
    {
      "application": "tests/sys/shell",
      "target": "native64",
      "toolchain": "llvm",
      "worker": "worker-1",
      "runtime": 12.3
    }
  ]
}
```

Murdock stores this free-form object in `JobModel.status` and broadcasts it on
`/ws/status`. The web UI uses it to show live progress and failure tables.

## Final aggregation

When all dwq jobs finish, `dwqc --outfile result.json` writes one JSON array
with the result of every subjob. `build.sh` then runs three steps:

1. `post-build.d` scripts read `result.json` and write extra files such as
   `sizes.json` and `metrics.json`, or print collected errors.
2. `process_result.py` converts `result.json` into the files the UI reads.
3. `gzip` compresses the raw `result.json` to `result.json.gz`.

### `process_result.py`

The parser in `common.py` reads each result:

| Field | Source |
| --- | --- |
| `status` | `result.status` is `0`, `"0"`, or `"pass"` |
| `worker` | `result.worker` |
| `runtime` | `result.runtime` |
| `output` | `result.output` |
| `name` | The command after the first token |
| `type` | `builds` for `compile`, `tests` for `run_test`, otherwise the name |
| `application` | Command argument 2 |
| `target` | Board part of command argument 3 |
| `toolchain` | Toolchain part of command argument 3 |

`process_result.py` writes:

| File | Contents |
| --- | --- |
| `builds.json` | One row per application with build counts and failures |
| `build_failures.json` | Flat list of failed build targets |
| `tests.json` | One row per application with test counts and failures |
| `test_failures.json` | Flat list of failed test targets |
| `stats.json` | Total build and test jobs, total worker runtime, and per-worker statistics. Static tests are not counted. |
| `output/builds/<app>/app.json` | Per-application build jobs and failures |
| `output/tests/<app>/app.json` | Per-application test jobs and failures |

The reporter writes the per-target text files before this step. `process_result.py`
writes the JSON summaries and application files.

The job also keeps `output.txt` for the top-level script output and any
declared artifacts such as `doc-preview/`.

## How the UI uses the aggregate

The `murfrog` UI reads both live and final data:

- while the job runs, it uses `status.failed_builds` and
  `status.failed_tests` for progress,
- after the job finishes, it reads `builds.json`, `tests.json`,
  `build_failures.json`, `test_failures.json`, and `stats.json` from
  `/results/<uid>/`,
- the result tabs map to builds, tests, output, artifacts, stats, and details,
- a per-application page reads
  `/results/<uid>/output/<type>/<app>/app.json`.

If a final file is missing, the UI can fall back to the live status arrays.
This matters for stopped or partially completed jobs.

## Failure handling

RIOT uses two different failure controls:

- `dwqc --maxfail` controls how many subjobs can fail before the job list
  stops. `build.sh` sets `DWQ_MAXFAIL=0` in fast-fail mode and `500` when the
  `CI: no fast fail` label or nightly mode disables fast fail.
- `.murdock` uses `--maxfail 1` when it queues a hardware test job, so a failed
  test does not run more tests on the same board queue.

Murdock also has a separate per-repository `failfast` option. When
`.murdock.yml` sets `failfast: true`, the server stops the job as soon as the
status contains `failed_jobs`, `failed_builds`, or `failed_tests`. This is not
the same control as RIOT's `CI: no fast fail` label.

The final job state comes from the script exit code, not from the aggregate
counts. `build.sh` exits with the `dwqc` result. Murdock maps a zero exit to
`passed` and a non-zero exit to `errored`.

## Worked example

A pull request that changes `tests/sys/shell/main.c` selects that application
and its matching siblings. On a quick build, RIOT builds those applications for
the quickbuild board list and emits one static test job. The aggregate job
shows one pass or fail per build and test, while Murdock stores one job with one
UID.

A merge-queue branch uses all supported boards. If a base commit is available,
change detection can still narrow the application list. The aggregate is much
larger in either case, but it is still one Murdock job.

## Why this matters

This design keeps the Murdock API and database small. One CI run produces one
job record, one status stream, one result directory, and one GitHub status.
The cost is that the server does not know the individual subjobs. RIOT must
emit the aggregate status and result files. Any tool that consumes Murdock
results must read both the job status and the files under `/results/<uid>/`.
