## What Murdock does

At its core, Murdock connects a Git forge to a pool of jobs. A pull request (PR) is a GitHub change proposal. A webhook is an HTTP callback from GitHub. A job is one CI run for a commit. A worker is a process that runs jobs.

1. A webhook arrives for a pull request or a push.
2. Murdock checks the event against repository policy: ready labels, branch and
   tag filters, skip keywords, and the configured repository.
3. It creates a job, fetches the `.murdock.yml` configuration for the exact
   commit, and puts the job on a queue.
4. A worker runs one or more tasks. A task is a shell script or a Docker container. The worker streams the output back to the API.
5. When the job finishes, Murdock stores it, updates the GitHub commit status,
   optionally comments on the pull request, and sends notifications.

## Two generations

The documentation distinguishes two architectures that are easy to confuse:

- murdock-ng (this server): an asyncio/FastAPI application with in-process
  workers, MongoDB/PostgreSQL history, WebSockets, and per-repo `.murdock.yml`.
- Legacy dwq Murdock: the older control-node + `dwq`/`disque` + worker-fleet
  design. RIOT's `murdock-scripts/build.sh` and the `murdock-worker` repository
  belong to this history. They are documented where they explain RIOT CI
  behavior, but they are not required to run the modern API.

## Version note

The API reference is generated from an OpenAPI 3.0.2 schema served by Murdock at
`/openapi.json`. The bundled snapshot matches the `murdock` submodule used by
this repository (version `1.0.0` of the API document). If you point the guide at
a different Murdock build, refresh the snapshot with:

```sh
cd docs
npm run update-openapi
```
